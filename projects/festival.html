The idea

Most class database projects stop at a schema and a few SELECT statements. This one is wired up to a live web app — a Shiny for Python front end themed as a board-game-styled Atlantic City boardwalk festival, "Rock & Beach." Every tab (lineup, tickets, dining, hotels, the grounds map) reads from the same PostgreSQL database, so the app is only as good as the queries and constraints behind it.

Why it's more than a toy schema

The database enforces its own rules

Rather than checking for scheduling conflicts in the app code, a PostgreSQL trigger on the attendee_performance junction table rejects any INSERT that would double-book an attendee into two overlapping performances on the same day — using Postgres's native OVERLAPS operator. The data stays consistent no matter what inserts it.

What I built — the front end

A 12-tab Shiny for Python app covering the full attendee experience: Lineup, My Schedule, Tickets, Activities, Dining, Hotels, a Grounds Map, Sponsors, a Group Planner, Social Match, a FAQ ("Good to Know"), and a personal "My Festival" profile. I wrote the HTML-rendering helpers that turn query results into the lineup cards, the visual schedule builder, the sponsor tiers, and the board-game-styled grounds map — plus the theming that gives the whole thing its Monopoly-boardwalk look.

SQL techniques behind the tabs

Lineup & Tickets

Multi-table JOINs

performance ⋈ artist ⋈ venue ⋈ festival_day, plus LEFT JOIN + GROUP BY for ticket availability

Social Match

Self-JOIN

Joins the vote table to itself to surface attendees with overlapping taste

My Schedule ✦

Trigger + window function

OVERLAPS trigger blocks conflicts; LEAD() finds downtime gaps between picks

Designed to degrade gracefully

🔌 Live-first

Every tab queries the real, deployed PostgreSQL database by default.

🛟 Mock fallback

If the DB connection fails, each tab swaps to built-in mock data automatically — the demo never shows a blank screen.

Honest limitations

  • Ticketing & voting: the attendee/ticket_type/ticket/vote tables are live but still 0 rows — those tabs run on mock data by design until that data exists
  • Group Planner & Social Match: reference tables that were never built in the final schema, so they're demo-only for now
  • Distance calc: the activity/restaurant recommendations use a flat-plane approximation, not true great-circle distance — fine for a compact boardwalk, not for a bigger venue
